# 排版、改写与 AIGC 检测收费

管理员在 `/admin/affiliates` 的“服务价格设置”修改价格；需要现有管理员登录。

| 服务 | 默认售价 |
| --- | --- |
| 论文排版 Word 导出 | 沿用 `THESIS_FORMAT_PRICE_CENTS`，未设置时为 29.99 元 / 篇 |
| 文本 AIGC 检测 | 0.99 元 / 次 |
| 文件 AIGC 检测 | 3.99 元 / 次 |
| 改写、降重、降 AI、双降 | 1.00 元 / 千字符 |

改写按非空白字符计数（中文、字母、数字、标点均计入），按实际字符数比例收费，向上取整到分，最低 0.01 元。例如 1001 字符为 1.01 元。Word 改写只接收 `.docx`，服务端从正文 XML 计数；旧版 `.doc` 请先另存为 `.docx`。检测按次收费，不按字数。

价格、报价、处理状态及可恢复的结果存储在 `ALIPAY_ORDER_DB` 指定的现有 SQLite 数据库中，部署时保留该数据卷。默认值只用于尚未设置的价格；后台排版价格优先于环境变量。调价不改变已生成报价或排版支付订单的金额，未付款报价有效期 15 分钟。

## 用户流程

1. 输入正文或上传文件，选择处理模型或检测平台，点击“计价并创建付款订单”。
2. 核对服务、字符数与应付金额，进入支付宝电脑网站收银台付款。
3. 返回原页，点击“我已付款，开始处理”。只有经过现有支付宝验签、商户和金额核验的成功通知才会放行。
4. 文件异步改写提交后查询对应任务；同步和流式结果可通过原订单恢复，无需重新付费或再次调用上游。刷新后保留当前标签页的订单信息；尚未提交的订单需恢复原文、文件和处理选项。

付款绑定具体操作、参数、文件名和文件内容摘要，不能更换论文或模型复用。SQLite 原子更新保证每笔付款只提交一次；异步查询只能查询该订单取得的任务 ID。其他开发接口不对网站用户开放。模型和平台目录仍可免费读取。

服务订单不接受优惠券，现有排版学校券及平台券行为不变；推广归因及付款后佣金结算复用现有支付流程。

## .doc 的字数怎么算（降 AI / 文档改写）

文档改写按字数收费，报价时要先数字数。`.docx` 读内部 XML 精确数；`.doc` 是二进制格式，由 `core/doc_binary.py` 直接读（毫秒级，不需要 LibreOffice，两台服务器都能用）：

| 情况 | basis | 字数 |
|---|---|---|
| 正常的 Word 97-2003 | `doc` | 按 FIB → CLX → piece table 取正文，去掉域指令和控制字符，数非空白字符 |
| 容器能打开但读不出正文（加密、Word 6/95、结构异常） | `estimate` | 按正文流大小估算：`(流大小 − 20000) / 6.5`，不少于 100 |
| 连容器都打不开（RTF、网页另存的 .doc、损坏） | `estimate` | 按文件大小粗估：`大小 / 16`，限制在 100～60000 |
| 扩展名写成 .doc 的 .docx | 无 | 当 .docx 精确数 |

**原则：读不懂也不让报价失败，宁可少收。** 估算的系数都取偏大值，在已知文档上估出来比真实字数少 16%～51%，不会多收；如果之后服务商拒绝了这份文件，会像其他失败订单一样自动退成积分。空文件仍然会明确拒绝。

实测准确度（同一份内容另存为 .doc 后与 .docx 的数法比较）：4 份论文是 0%、0%、0%、−0.04%（差 8 字），一份真正的 Word .doc 与 LibreOffice 转换后的数法完全一致。样本不多，复杂 .doc（脚注、文本框、修订）没测，所以报价时页面会提示"可能有小误差"。

**价格调整比例**：环境变量 `THESIS_DOC_PRICE_PERCENT`（默认 0，范围 −90～200）只作用于 `.doc` 的报价：`金额 = ⌈字数 × 单价 × (100 + 比例) / 100⌉`。想再让利就设成负数，例如 `-5` 是 95 折。报价接口会返回 `approximate`、`basis`、`adjust_percent`，页面据此显示说明。

提交给服务商的仍然是用户上传的原始 `.doc`（服务商接口文档标明支持 .doc；真实付费调用的效果需要上线后用一份很小的 .doc 实测）。

## 异常核查

后台“最近服务订单”显示最近 100 条报价 / 支付订单。`failed` 或一直 `processing` 的已付款订单需要人工核查上游及支付宝流水。浏览器断网或进程退出后，不得直接把订单改回可提交状态，避免上游已受理后重复扣费。

### 失败时怎么处理

对服务商的请求分阶段：`connecting`（TCP + TLS 握手，上限 30 秒）→ `sending`（送文件）→ `waiting`（文件已送达，等结果）。页面处理中每 2.5 秒问一次订单状态，状态里带 `progress`，用户几秒内就能知道文件有没有送到。

| 失败发生在 | 文件到服务商了吗 | 怎么处理 |
|---|---|---|
| 连接阶段（握手超时、连接被拒） | 没有，一个字节都没发 | 自动重试一次；仍失败就把订单恢复成 `ready`，**不退款也不标记失败**，付款仍有效，用户稍后用同一笔付款重新提交（`NotDelivered`） |
| 连上之后（送文件中、等结果时、超过总时长） | 可能已到 | **不重试**，标记 `failed` 并退款，见下 |

总时长上限 `TABWORD_DEADLINE_SECONDS`（默认 180 秒）由看门狗强制执行：到点直接掐断连接，服务商一点一点地回数据也拖不过它；线程的截止时间比外层等待早 2 秒，原因由线程如实报告。

**失败退款一律退成积分**（`core/points.py` 的 `refund_failed`）：

- 积分付款：退回当初扣的积分。
- 支付宝付款：按付款金额退成同额积分（1 元 = 10 积分），用户马上能用积分重试。每笔订单只退一次（流水 `refund` + `alipay:<订单号>` 唯一）。**不动支付宝里的钱**；如果又人工退了现金，要先把这些积分扣回，免得退两次。
- 匿名报价（没有账号）退不了积分，报警邮件会写明，需要人工退款。

## 验证与部署

离线测试：`python -m unittest discover -s tests -q`。测试使用模拟支付和上游，不产生真实订单或 API 费用。上线仍需在公网环境验证支付宝成功通知和完整业务流程。

更新代码后重新构建并启动原部署栈：`docker compose up -d --build`。已有本地 Python 进程不会自动加载后端改动。无新增密钥或环境变量。
